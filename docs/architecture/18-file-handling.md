# 18: File handling

This chapter covers file handling. A file's metadata travels as an ordinary synced row and its bytes travel on a separate channel with their own storage, their own tickets and their own abuse surface. It covers the boundary with the row-sync crates, file identity, chunking and the manifest, the client's encrypted stores, display through signed URLs, the server's chunk store and sweep, tickets and the mint, two-phase upload and the availability signal, and the abuse surface. The capability distinction behind the ticket is recorded in [12-identity-session-capability.md](12-identity-session-capability.md#a-content-ticket-is-not-a-capability), the client connection in [13-client-connection.md](13-client-connection.md), key custody and teardown in [14-at-rest-encryption.md](14-at-rest-encryption.md), eviction and pins in [15-replica-retention.md](15-replica-retention.md), and backup and restore in [20-deployment.md](20-deployment.md).

## The boundary

The boundary is the crate, not the repository. The file crates live in this repository beside the demos, depend on connetto and never the reverse, and the demos carry the feature end to end. `connetto-core` carries exactly one seam toward file handling, the signer trait described under [The wire, tickets, and the mint](#the-wire-tickets-and-the-mint).

The shipped executable serves files. `connetto-server` takes `connetto-file-server` behind a default-on `content` feature, and the builder mounts the four file routes, the intent, the chunk `PUT`, the commit and the download, beside the sync route and the login endpoints on the one listener. It builds the ticket signer and verifier from one keypair in one process so no key crosses a process boundary, and it gives the file router its own admin and reader pools so uploads never compete with the change stream for the owner pool. The sweep runs on a cadence, and with `CONNETTO_CONTENT_URL` unset the builder keeps [`connetto_server::ContentSigner`] `None` and no routes. No connetto library beside the server depends on a file crate, and a file-only executable over the same [`connetto_file_server::Config`] is additive the day a deployment scales files out.

In the browser a tab stages by attaching the bytes to its own mutation. The tab computes the file identity itself, writes the metadata row on its mirror as an ordinary captured mutation, and the bytes ride the tab's internal wire as an attachment, a `Blob` that crosses to the worker without a copy. The worker runs `stage` with the tab's changeset as the row closure, so the manifest, the outbox entry and the row commit in one transaction exactly as natively, and a file identity that disagrees between tab and worker rejects the whole mutation through the existing rollback path. Resolving is a correlated request on the same wire answered with a signed URL, a `Blob` the tab turns into an object URL it owns, or unavailable. The server protocol is untouched.

The file crates own the traits with more than one implementation. [`connetto_file_core::ChunkStore`] has `write_chunk`, `read_chunk`, `has_chunk` and `delete_chunk` by content hash, with OPFS, `std::fs`, in-memory and object-store implementations, and the content sources an application resolves a file through sit behind [`connetto_file_client::LocalContentSource`].

A store never decides that a chunk is unreferenced, because two manifests can name the same chunk, so that judgement stays with whoever holds the manifests. Manifest and outbox bookkeeping are plain tables rather than an abstraction over them, with one implementation on each side of the wire. On the client they sit in the replica beside the rows they commit with, the `_connetto_content_chunks`, `_connetto_content_outbox`, `_connetto_content_retired` and `_connetto_content_pins` tables, plus the `_connetto_held_content_outbox` and `_connetto_held_content_chunks` pair that holds content per application schema major. On the server the file server's Postgres schema holds `_cfs_manifests`, `_cfs_manifest_chunks`, `_cfs_chunk_registry` and the per-day `_cfs_traffic` ledger. The case that would have needed a second manifest implementation is a peer content source, and it needs a content source rather than a manifest store.

A store that can list what it holds implements [`connetto_file_core::ChunkInventory`] beside `ChunkStore`. The client's `std::fs` store, the in-memory store and the browser's OPFS store all can. A deployment's object store is not asked to, because it holds every file every caller ever uploaded, so answering "all of it" as one list is the wrong shape at that size, and the server sweeps from the chunk registry it already keeps. `delete_chunk` belongs on `ChunkStore` itself, because every store can be pruned and a store that can be written and not pruned is a store whose disk only grows.

## Identity, chunking, and the manifest

A file's identity is the plain BLAKE3 hash of its bytes, computed in the same streaming pass as chunking. It is deliberately chunking-independent. BLAKE3 is internally a Merkle tree, so verified range streaming (bao) remains a later upgrade with no format change, anyone can recompute the identity with `b3sum`, and re-tuning chunk sizes never re-identifies a file. A hash over the chunk hashes is refused, because that identity silently depends on the chunking parameters.

Content is split by FastCDC under a per-mime-class parameter table shipped as data, and a file at or under the maximum chunk size skips chunking. Compressed formats (JPEG, video, gzipped scientific data) get large parameters or whole-file treatment, because sub-file dedup finds nothing in them. The manifest is the ordered list of per-chunk (BLAKE3, length) pairs, transport and dedup metadata only, lengths present because they map a byte range to chunks.

Each chunk is zstd-compressed (level 3, per-mime skip table, a compression flag in the chunk header) between chunking and encryption. The dedup hash is always over plaintext. Text-heavy scientific data roughly halves under zstd, and the driving use case is exactly that.

connetto keeps no file tree. The name and the path of a file are columns the application holds on its own metadata table, a rename or a move is an ordinary row conflict, and the file-tree question is closed by construction, because no tree exists to ask.

## Client storage

One encrypted chunk store outside SQLite. Chunk files in OPFS in the browser, plain files natively, each XChaCha20-Poly1305 ciphertext under a random 24-byte nonce stored with it, the chunk's plaintext hash as the authenticated data, and the key derived by BLAKE3 key derivation with a purpose label from the same custody [`connetto_core::ReplicaKeyStore`] serves, so the [unlock gate](https://github.com/connetto-rs/connetto-rs/blob/82983dff19effa9cfb521370a7794d29e51afb51/plans/master-implementation-plan.md#r23-user-verified-unlock-of-locally-stored-secrets) and the crypto-shred on wipe cover content exactly as they cover the replica. The cipher is XChaCha20-Poly1305 over AES-GCM, because the 192-bit nonce removes the birthday bound on nonces, it is one shared pure-Rust layer on every target where the replica cipher is two (SQLCipher native, sqlite3mc wasm), and it makes no AES-NI assumption on mobile cores.

The manifests and the upload outbox live in the replica, committed in the same transaction as the entry row, so a crash orphans a chunk file (collected by the sweep) and never commits a row pointing at bytes that were never written. SQLite never carries content bytes on either side of the wire.

The device-private tier cannot hold them, because the incompatibility is silent. The replica opens with `PRAGMA journal_mode=WAL` before the tier is attached, the two are separate files, and SQLite's atomic commit spans attached databases only while no database in the set is WAL. A transaction writing both files commits with no error, and a host crash inside that commit may update one file and not the other. That is the correction [R20](https://github.com/connetto-rs/connetto-rs/blob/82983dff19effa9cfb521370a7794d29e51afb51/plans/master-implementation-plan.md#r20-connetto-must-not-require-a-reachable-server-to-start) made for the same problem, and the tier is optional and defaults to absent, so a tier-resident manifest would make file handling unavailable to any client that did not ask for one. The content tables carry the `_connetto_` prefix that already marks connetto's own bookkeeping in the replica, beside `_connetto_meta`, `_connetto_pending` and the subscription set, which keeps them out of capture, out of the tier's application-table listing and off the wire.

Client content divides into two classes. Unsent content, authored here and not yet uploaded, is data, and its chunk files travel in the [device archive](https://github.com/connetto-rs/connetto-rs/blob/82983dff19effa9cfb521370a7794d29e51afb51/plans/master-implementation-plan.md#r26-local-data-export) by manifest walk, because an unsent write cannot be refetched. Fetched content is cache, evictable under the pin rules, never exported, refetchable by construction.

A data wipe removes the content store with the replica, on both platforms. The store is one more thing the replica key opens, so it is on the list [chapter 14 keeps under Teardown](14-at-rest-encryption.md#teardown), and it is found by derivation like the tier. `db_path-content` natively, where the demos build their `FsStore`, and in the browser the per-account namespace, the `sha256(seed, replica_db_name)` the pending-wipe record carries. The namespace being per account is what makes the removal safe. No second identity on the device can hold chunks under it, and an anonymous boot opens none.

The browser store belongs to the dedicated database worker and reacquires its `OPFS` root for each operation. A new chunk closes under an unreportable temporary name before an atomic move exposes its hash, and opening the namespace removes interrupted temporary names. An existing hash is replaced through `createWritable` and `close`. An environmental `OPFS` failure selects a worker-lifetime memory store, while an invalid namespace fails installation. That fallback refuses writes, because the replica would record a manifest and an outbox entry for bytes that die with the worker and the next boot would find them gone. It holds nothing durable either, so every read misses, and a missing read there is inconclusive rather than a loss, which is what preserves the outbox entries whose bytes are sitting in an `OPFS` namespace this run cannot open. A store the application chose as ephemeral accepts its own writes, because nothing there claims durability. An anonymous run always selects memory, so the bare replica name never leaves durable content. An authenticated namespace is the lowercase SHA-256 of the configured seed and replica identity, preventing account switches from opening ciphertext under the wrong key. A destructive logout persists that exact namespace even when the current backend is memory, and the next worker removes it recursively once the key, the tier and the replica are gone.

Device archives declare every entry and its per-entry encoding. Unsent content travels as a plaintext `content/manifests.json` plus one `content/chunks/<hash>` entry per distinct chunk, while fetched and pinned cache stays behind. Import validates the exact ZIP layout, lengths, hashes and reconstructed file identities before writing through the receiving [`connetto_file_core::EncryptingStore`], then commits application changes, manifests and outbox entries in one SQLite transaction. A connected importer replays the restored mutation queue before the content driver can request visibility-gated upload tickets. A generic importer refuses nonempty attachments, and the content importer refuses any path outside `content/`.

An archive costs one chunk of memory in either direction, on either platform. The archive reader takes a seekable source and yields entries one at a time, the content importer writes each chunk through the encrypting store as it is read, the archive writer takes a plain `Write` sink through `ZipWriter::new_stream`, and the exporter reads each chunk from the store as its entry is written. In the browser the import source is the tab's `Blob`, which crosses `postMessage` without a copy and is read through `FileReaderSync`, the one synchronous seekable read a dedicated worker has. The export sink is a `Blob` grown by concatenation, which the browser keeps as a list of parts and spills to disk on its own, so no temporary file exists and nothing is left to clean up. Natively both ends are files.

Streaming cannot validate a chunk before its bytes have been read, so the content importer reads the seekable source twice. The first pass walks every file's chunks in the order its manifest names them, checking each declared length, each chunk hash and each reconstructed file identity, and writes nothing anywhere. The second pass writes each distinct chunk through the receiving store, rechecking its hash immediately before the write, because the source belongs to the caller and a file on disk can be rewritten between the passes. The entry checksum the reader recorded when the archive was opened refuses an ordinary rewrite, and the recheck refuses one that keeps that checksum, because the `write_chunk` of [`connetto_file_core::EncryptingStore`] binds the ciphertext to the hash it is handed rather than recomputing it, and a chunk stored under a name its bytes do not hash to is content the device can never resolve. An import refused by validation leaves the store exactly as it found it. Chunk entries are stored uncompressed, so the second pass costs a raw read rather than a second decode, and one chunk is in memory at any moment in either pass. Two things can leave addressed chunks nothing references, a failure of the store itself and a source that changes under the writing pass, and in both the chunks written before the refusal stay until the orphan sweep collects them.

The bounds on an archive are the two the client publishes, [`connetto_client::archive::MAX_ATTACHMENT_BYTES`] at 256 MiB for one entry and [`connetto_client::archive::MAX_ATTACHMENTS_BYTES`] at 2 GiB across attachments. The reader decides both from the central directory before it reads an entry's body, on either platform, and the export path weighs unsent content against the aggregate before it starts writing, which is the same bound the writer enforces per declaration and buys a refusal that names the byte count.

Each compressed row entry in the archive, `synced.patchset`, `device-private.patchset` and `pending.changesets`, decompresses through a streaming decoder bounded at the 2 GiB ceiling the attachment aggregate already names, applied per entry rather than in aggregate, so the two paths share one figure for what an archive may ask a device to hold in memory.

`pending.changesets` carries each queued write's writer, sequence and chain hash, plus the original writer and sequence as provenance when the write was first made under another writer. An import re-queues the restored writes under the importing replica's own writer, each taking a fresh sequence and chain hash in that writer's chain, and retires the archived writers through the ordinary [`connetto_core::messages::RetireWriter`] sends, the obligation persisted per distinct archived writer, so the server's frontier keeps deduping the logical write across the restore. Each queued write and each provenance also carries the secret its number writer was issued under, so an import names that number to the server under its own secret, with the capture majors [13-client-connection.md](13-client-connection.md) states.

A permanently refused upload stays in the outbox, marked with its refusal detail, and is not attempted again until the application asks. Presence in the outbox is what makes content unsent rather than cached, so every consumer that reads the outbox, the pending work answer, the export walk, the wipe guard and the device tier, inherits the right answer with no change. A refusal is a fact about the deployment's configuration rather than about the file. The ceiling lives in the ticket the deployment mints, part of it per identity through the rolling bandwidth rate, with a per-identity quota on top, so an operator raising a budget or a person freeing space makes the same upload succeed. The cost is stated rather than hidden. The outbox now means not yet sent rather than will be sent, so every count includes refusals, and a caller that wants only the sendable entries asks for those. A file too large for its deployment sits there and blocks a non-forced delete until the application retries it, drops it, or the person forces the delete.

A permanent upload outcome is one of two events, and which one is decided by where the fact comes from. A refusal is an answer from the server, a `400`, `413` or `422`, an undecodable reply or a malformed grant, so the entry stays in the outbox and the application sees [`connetto_file_client::ContentEvent`] `UploadRefused`. A loss is a fact about this device, a manifest the outbox names that the replica no longer holds or a chunk the store cannot read, so the entry is retired and the application sees `BytesLost`. Retiring an outbox entry destroys the only record that this device declared the file, so the identity is written to `_connetto_content_retired` in the same transaction as the dequeue and reported by every pending-work answer until the application acknowledges it. The integrity scan already retires a missing manifest, and the upload walk retires it the same way rather than routing `NoManifest` through the refusal path, where a retry on request could only fail identically, so the event the application receives for one fact is the same whichever pass found it first. The outbox driver schedules walks from the sendable count, which excludes refused entries, so a refused file never triggers a walk on its own. When the application clears a refusal through `retry_refused`, the driver is notified exactly as an import notifies it, natively as in the browser, so the cleared entry is attempted without waiting for a reconnect, a mutation or a new import.

## Display is not sync

The common case renders a short-lived signed URL and never touches client chunk storage. The file server assembles from chunks and serves plain HTTP with `Range` mapped through the manifest, a strong `ETag` equal to the content hash, and immutable caching, so the browser's own cache, progressive rendering and video seeking do their jobs. Local content sync happens in exactly three cases. Pinned files, the byte-level mirror of [the row pins](15-replica-retention.md), locally processed inputs, a FASTA or MGF parsed in wasm needs bytes or ranges, and content this device authored but has not uploaded.

In the browser, HTTP uses the worker `fetch` for the same request shapes as the native transport, with the chunk `PUT` through `XMLHttpRequest`, the one portable source of upload progress in a worker, and only its body is large enough for the send to need observing. The intent body is the manifest, about a hundred bytes per chunk, and the commit carries no body, so the `POST` through `fetch` shares the download's streamed reply reader and its timer. Ticket URLs require HTTPS except for loopback HTTP, and redirects are refused. Local bytes become an `ObjectUrl` owned by a reference-counted handle, and the browser URL is revoked when its last owner drops. Remote resolution remains the signed server URL.

A content transfer is bounded by silence. One idle bound, thirty seconds by default, covers every phase of a request on both platforms. The transfer aborts when no byte has moved in either direction for that long, and a moving transfer is never aborted however long it runs. A valid chunk is 16 MiB and a download collects a whole file, so any total deadline is a floor on link speed that some link is below, and a transfer that fails it restarts from byte zero on every retry. The bound is one number because the silence after the last request byte, while the server verifies a chunk or runs the commit's whole verification, is the same silence to the client, so a deployment with a slow commit raises its bound rather than getting a second one. A deployment sets it through `with_transfer_idle_bound` in the browser, in [builder.rs](../../crates/connetto-web/src/builder.rs), and through [`connetto_file_client::Content`] `with_transfer_idle_bound` natively, and a native application that passes its own `reqwest` client through `with_client` keeps that client's settings, since the point of that constructor is proxies and certificates the application already configured. The bound in every situation a transfer can be in.

| Event | Sending the body | Waiting for the status line | Receiving the body |
|---|---|---|---|
| Bytes move | Timer reset, except a browser `POST`, whose send shares the status wait's window | Not possible | Timer reset |
| Idle bound elapses | Abort, retryable | Abort, retryable | Abort, retryable |
| Status line arrives | Not possible | Timer reset, then receiving | Not possible |
| Body ends | Timer reset, then waiting | Not possible | Reply complete, timer cleared |
| Network failure | Retryable | Retryable | Retryable |
| Redirect, as a `3xx` reply or a reply landed on another URL than the request | Not possible | Refused, permanent | Refused, permanent |
| Local relay request | Served, transfer continues | Served, transfer continues | Served, transfer continues |

An abort is `Transport` and therefore retryable, because an unsent write cannot be refetched and a stalled link is exactly the ambiguous failure the outbox bias keeps. A reply from another origin is permanent under the two-event rule above, since it is an answer about the server, and the HTTPS or loopback validation of the ticket URL still runs first. Browser downloads read the response as a stream and reset the timer per received chunk. Browser uploads run through `XMLHttpRequest`, whose unconditional redirect following is why the origin of the landed reply is checked afterwards, where `fetch` refused the redirect before. Native downloads and uploads both stream, and the native transport keeps its own watchdog and asks nothing of the `reqwest` client.

In the `reqwest` client the read timeout restarts on every received frame of the reply, but on the request it is one sleep started at `send` and polled until the status line arrives, with no reset while the body goes out. On a client that also uploads that is a total deadline on the send of a chunk, the floor on link speed the idle bound removed, and no per-request setting switches it off. The native transport therefore carries the idle bound itself, thirty seconds by default and set through its own builder, and enforces it with one watchdog per request. The upload body goes out as a stream whose every pull is a write the connection accepted, and the reply body is read as a stream whose every chunk is a receipt. Both feed the same watchdog, and the request future is abandoned when the watchdog sees the bound of silence in any phase, including the wait for the status line. The pull is a buffer ahead of the wire. The connection pulls a frame when its own write buffer has room and the TLS and kernel send buffers sit below that, a few MiB together. After the last pull those bytes drain unseen, so the silence the watchdog measures before the status line is the buffered tail over the link rate plus the server's verify, and a link slower than the buffered bytes over the bound has its upload tail aborted while still moving. That is the one floor on link speed that remains natively, about a megabit per second at the default bound. A client built with `new` carries no timeout of any kind, and `with_client` keeps the application's client untouched under the same watchdog, so a proxy or certificate the application configured reaches every request.

A redirect is a refusal on every path, and it has one name. The native transport's own client follows no redirect, the same rule browser `fetch` keeps, because the mint issues exact URLs and no hop is part of the protocol. `reqwest` replays a `Vec` body to a redirect target and never a streamed one, and its redirect layer returns the reply of a `307` or `308` on an unreplayable body to the caller before the policy runs, so a policy that inspects the hop would never see the one on a chunk upload and a policy that follows would resend the intent manifest to a foreign origin before any check. With no following, every `3xx` reply reaches the negotiation on the ticket's own origin and is refused there beside the other status decisions. Two paths still follow. An application client passed through `with_client`, whose policy is its own, and `XMLHttpRequest`. Both compare the landed URL of the reply with the request URL afterwards, as parsed URLs, so any redirect they followed is refused whatever its origin, and only a chain that lands back on the ticket URL itself passes, which is where the ticket pointed. Browser `fetch` asks for the `manual` redirect mode, whose opaque reply is distinguishable where the `error` mode's rejection is the same failure a dropped connection raises. The refusal is `ContentError::Redirected` with the stage and the origin of the landed reply when one landed, nothing when the redirect was refused before landing, and `outcome` classifies it `Refused`. What the refusal detail stores is the origin rather than the landed URL, because a landed URL can carry the ticket in its query and the detail is stored. The URL comparison sits in the two transports that hold a landed URL, while the status rule sits above the seam.

The ticket URL is validated once, above the transport seam, on both platforms. A grant must be HTTPS, or HTTP on a loopback host, before any request leaves, because the ticket rides the URL query and a rewritten scheme would carry it in clear off the machine whatever the mint refused to sign. The rule runs where the grant's shape is already checked, beside the split of the write URL into its three addresses and at the entry of a download, with the parsed host rule the mint keeps rather than a text match, and a failing URL is `MalformedGrant`, an address that is not the shape the file server mints, permanent under the two-event rule.

A file reference row is an intent. Metadata can arrive before content is fetchable, offline authorship makes that unavoidable, and readers show a placeholder until the availability signal below flips. Thumbnails are ordinary derived files behind a `thumb_hash` column, one pipeline with everything else.

## Server storage

Content bytes never enter Postgres. This deployment runs `wal_level = logical`, so `BYTEA` content would be fully WAL-logged and pinned by the [replication slot](10-subscription-materializer.md#the-replication-slot), letting one bulk upload eat the retention headroom that keeps offline devices resumable. Chunks live in a filesystem directory or an S3-compatible object store behind the same [`connetto_file_core::ChunkStore`] trait. Manifests stay in Postgres through typed diesel, and chunk liveness is derived from the `manifest_chunks` references, with no counter maintained. Garbage collection is mark-and-sweep. The sweep locks candidate registry rows, discards those still referenced by any manifest, committed or within the grace window equal to the upload ticket lifetime, and marks the rest deleting.

A database backup restores every metadata row and no bytes, so the chunk store needs its own backup, and [20-deployment.md](20-deployment.md) states the pairing and owns the wider backup and restore story.

Before the listener opens, [`connetto_file_server::reconcile_store`] lists the chunk store, deletes chunks no registry row names once past the grace window, and marks lost every committed manifest naming a chunk whose bytes are gone. A lost manifest is uncommitted, so it is not served and dedup does not count it, and the sweep never collects it. Its missing chunks go back to `pending`, and the deployment's setter hears `lost` under each uploader's attributions, so a setter must accept that state or the boot stops naming the file.

The application registers where `lost` shows with [`connetto_file_client::Content`] `with_heal_lost` natively and `with_content_heal_lost` in the browser, in [builder.rs](../../crates/connetto-web/src/builder.rs), for example `SELECT content_id FROM photos WHERE content_state = 'lost'`. A device holding a named file puts it back in its outbox. The commit that heals it restores every lost manifest under the committer's verified chunks and their own uploaders, and deletes a healer's own manifest, so quota and ownership stay where they were. A server restarted after the bytes of the files it names were deleted from the chunk store is the proof in [photo_heal.rs](../../examples/wasm-smoke/tests/photo_heal.rs).

A device keeps a file while it is unsent or a pin names it, natively and in the browser alike. A tab pins through `TabContent::pin_content`, `unpin_content` and `content_pins`, in [content.rs](../../crates/connetto-web/src/content.rs), which the worker answers from the same pin records [`connetto_file_client::ContentClient`] `pin_content` keeps natively. The native outbox driver runs `tidy_content` after every pass that sent a file, as the worker runs its retention pass after an upload, so an uploaded file no pin names leaves both platforms by itself. A file queued for healing is an outbox entry of the heal kind rather than an authored one. It is dropped before upload once no heal query names it, dropped quietly without a `BytesLost` when its local bytes cannot be read, left out of the export and of the pending counts, and never evicted while queued, and it becomes an authored entry, keeping any refusal, when the same file is staged or imported here. The sync server mints the write ticket on the caller seeing the row, so any device that sees a lost file and holds its bytes heals it.

In the Yew photo pane, **Pin all photos** retains the files named by the live photo query. **Unpin photos** releases that pin, **Fetch pinned** downloads missing pinned bytes, and **Free up content storage** removes unpinned local bytes.

## The wire, tickets, and the mint

An `img` tag cannot present a grant, so the URL itself must prove the right to fetch. A content ticket is a transport ticket carrying an already-made decision from the websocket to HTTP. It is deliberately not a capability, [in the sense 12-identity-session-capability.md defines](12-identity-session-capability.md#a-content-ticket-is-not-a-capability), and the ticket is never presented at a handshake and never enters a `Principal`.

A ticket carries the deployment's fixed lifetime. The mint sets the expiry from the clock plus `CONNETTO_CONTENT_TICKET_TTL_SECS`, an hour by default, read by the server binary at boot, and the verifier accepts the ticket up to [`connetto_core::clock::SERVER_SKEW`] past the expiry, as [21-clocks.md](21-clocks.md) states. A ticket outlives the session that minted it, and a logout or a data wipe keeps a cached ticket readable for up to the TTL plus the skew, which is [G5](../../plans/master-implementation-plan.md#g5). A session that outlives the TTL re-mints, and its cached URLs die at the expiry.

What rides the websocket is the ticket request, file id, verb, and for the write verb the declared byte size, and its grant. The types are [`connetto_core::messages::ContentTicketRequest`] and [`connetto_core::messages::ContentTicketGrant`] on [`connetto_core::ControlMessage`], carrying [`connetto_core::messages::ContentVerb`] `Read` or `Write { declared_len }` and a caller-chosen `request_id` echoed by the grant and by any refusal. Connetto calls a deployment-wired signer, the `WriteTarget` pattern. The seam is [`connetto_core::ContentTicketSigner`], implemented by [`connetto_file_server::TicketSigner`], which holds the URL base, the ticket lifetime and the read ceiling, since a read carries no caller-declared size. The signer, its key, the token format and the verifying HTTP endpoint all live in one file crate, so no key material and no token vocabulary enter `connetto-core` beyond the seam trait. The whole upload negotiation, intent, needed-hashes, chunk PUTs, commit, is HTTP under that ticket, and the file server enforces the ticket's byte ceiling rather than keeping a second counter. Refusal details are [`connetto_core::messages::CONTENT_TICKET_REFUSED`] and `CONTENT_TICKET_SIGNER_ERROR`.

The mint asks the same visibility function the serving check asks. Connetto asks `connetto_visible_files` on the reader role, exactly as the dedup and serving checks do, and row level security and FGA decide the mint. Re-deriving the answer inside connetto from the application's own metadata row is refused. It needs a file-id-to-row mapping connetto does not have, and it lets the mint and the serving check drift apart, so a file could be mintable and unservable or the reverse.

The mint and the three file-server checks bind the whole caller, through the same `CallerBinding` shape, in [capability.rs](../../crates/connetto-server/src/capability.rs), as every other path. The caller crosses the seam as a value with two optional halves, the identity and the packed subjects, the `mint` of [`connetto_core::ContentTicketSigner`] takes that value, the ticket carries it, and the file server binds both under the setting names its `Config` carries, so a deployment that renamed either is answered under its own names rather than connetto's defaults. One binding function replaces the three inline `set_config` calls at the serve recheck, the needed-hashes answer and the commit dedup check. A caller holding neither half owns no manifest key, so a write is refused at intent rather than keyed on the empty string, and that key is also what `connetto_set_content_state` receives as its attribution. Binding the identity alone is refused. A caller holding a share key and no login could never obtain a ticket, and an unidentified caller would be bound to a blank identity, which is the shape [chapter 08's four-row arrival table](08-authorization.md#the-caller) forbids.

An invisible file and an over-budget request answer one byte-identical `NonFatalError` detail, the way `SUBSCRIPTION_REFUSED` stays identical across causes, so a caller cannot learn that a file it cannot see exists. A signer failure answers a distinct detail, because it discloses nothing about any user's data and a retry is meaningful where retrying an invisibility is not.

The mint refuses a base that is not HTTPS or loopback. [`connetto_file_server::ticket::TicketError`] `InsecureBase` is returned at construction for any `http` base whose host is not `localhost`, `127.0.0.1` or `[::1]`, so a misconfigured deployment fails at boot rather than minting interceptable grants per request.

## Upload, and the availability signal

Upload is two-phase. The intent declares the manifest, the needed-hashes answer lists the chunks the server does not have, the chunk PUTs send them, and the commit verifies dedup satisfaction, chunk hashes, the BLAKE3 identity, and that the committer is the manifest's original declarer. A half-uploaded file is never a servable version, and resume is re-sending the intent. Dedup satisfaction checks that every chunk is either stored through this upload or present in a committed manifest visible to the caller. That check runs as the reader role so RLS applies inside `connetto_visible_files`. A deployment whose function relies on RLS alone must have it run as a non-owner role, since the admin role owns the tables and bypasses RLS, which would silently accept invisible dedup targets. Committer identity is bound to the `uploaded_by` field written at intent time and refused with the same status as a failed visibility check, so no new status distinction reopens the existence oracle.

After commit the file server writes a `content_state` column on the metadata row, and CDC delivers the flip to every subscribed device with the row's own policy gating who learns it. That is a convention, deliberately not a trait. That write needs a grant nothing provides by default, because the file server's role is not the row's owner and the [security defaults](https://github.com/connetto-rs/connetto-rs/blob/82983dff19effa9cfb521370a7794d29e51afb51/plans/master-implementation-plan.md#r1-security-defaults) forbid superuser and `BYPASSRLS`. The deployment provisions a column-scoped `UPDATE` policy or a `SECURITY DEFINER` setter, verified at startup.

## The abuse surface

The content channel's read ceiling caps one response and the write ceiling caps one upload, enforced against the ticket's ceiling. [R19](https://github.com/connetto-rs/connetto-rs/blob/82983dff19effa9cfb521370a7794d29e51afb51/plans/master-implementation-plan.md#r19-request-throttling-tiered-by-identity) meters occurrences rather than bytes, and file upload is the system's first genuinely bulk write path. Refusals answer `404` whether a file is absent or forbidden, [the refusal principle](https://github.com/connetto-rs/connetto-rs/blob/82983dff19effa9cfb521370a7794d29e51afb51/plans/master-implementation-plan.md#r38-a-refusal-stops-disclosing-what-exists) on HTTP. The dedup negotiation's needed-hashes answer is scoped to the caller's own visibility domain, closing the existence oracle cross-user dedup would open, while storage dedups globally and silently. Convergent encryption is refused outright.

The upload direction carries windowed per-caller metering. Connetto charges a rolling bandwidth rate once at the mint, in [throttle.rs](../../crates/connetto-server/src/throttle.rs) beside the subscription, connection and credential limits. It stays in memory and adds no schema, because this is abuse prevention rather than accounting and a restart forgiving a few minutes of history is not an abuse vector. It charges the declared size, so the cap is on the bandwidth the deployment authorized rather than on what a link carries. Closing that gap would need the file server reporting actuals back to connetto, which is a second counter.

The window keys on whatever names the caller. The key is the identity when a login resolved, the caller's packed capability subjects when it did not, and the run's own session handle for an unidentified caller, the fallback the mutation byte meter already uses. A share-key holder gets its own window, and an unidentified caller is metered per run. The quotas are specified against this key, and a per-run window is deliberately weaker than a per-subject one, because a caller holding neither half has nothing durable to charge.

The storage quotas and the deployment ceilings live in the file server. A per-identity storage quota, a deployment-wide storage ceiling and a deployment-wide served-bandwidth ceiling, so an operator can say "we store at most 1 TB" or "we serve at most 1 TB a month". They belong here rather than in connetto because the numbers already do. `_cfs_manifests` carries `total_len` and `accepted_bytes`, and `_cfs_manifest_chunks` carries `chunk_len`, so stored bytes are knowable per uploader and deployment-wide, measured rather than declared, at the moment a commit makes them true. A ceiling refusal reaches the caller as the same byte-identical refusal and names the saturated ceiling only in the structured log, so an operator sees a ceiling filling instead of learning from a support ticket.

Two callers uploading identical bytes each hold their own declaration, so each is charged the whole file, and the deployment-wide ceiling is measured from real usage rather than by summing quotas. Per-user numbers therefore sum to more than the disk holds, which is intended. A user's usage never moves because a stranger uploaded or deleted the same content. Charging the deduplicated share is refused, because it makes one user's reported usage depend on what others store.

The ceilings are counted in Postgres over a rolling window, and a saturated request says which kind of full it is. The file server scales out, so its served and accepted bytes are upserted into a per-day table every replica shares, the window is a trailing duration, and each replica checks a cached sum refreshed on a cadence with the overshoot bounded and stated. A commit over the uploader's own quota answers `507`, because the user can delete something. A deployment ceiling answers `503` with `Retry-After`, because nothing the user does helps and the outbox and the resolver already treat that answer as transient. No answer reveals existence or visibility, and a ceiling reveals neither. A warning fires once when usage crosses a configured fraction of any ceiling.
